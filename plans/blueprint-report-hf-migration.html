What Just Happened — Plain English
What is a Blueprint?
A blueprint is a complete written plan — like an architect's drawing — created before a single line of code is touched. It maps out every step, in what order, which files change, what could go wrong, and how to recover. The idea is: spend 20 minutes planning properly so you don't spend 3 hours fixing a broken system at midnight.
What is the Adversarial Review?
After the blueprint was written, a second AI agent (running on Opus — the most powerful model) was given the plan and told: "Be harsh. Find every flaw." It came back with 4 critical issues and 7 high-priority issues. We then verified each one against the actual codebase. Some were real problems. Some were wrong. This is the difference between a plan written by one person and a plan pressure-tested by a critic.
Why did we switch to the OpenAI-compatible router approach?
HF exposes https://router.huggingface.co/v1 — an endpoint that speaks the exact same language as OpenAI. This means we keep the openai package already installed and only change 2 lines per file: the URL and the API key. Every .chat.completions.create() call stays identical. Fewer changes = fewer places for bugs to hide. For a production healthcare system, this is the right call.

The Plan — 7 Steps

What we will do, in order

Key rule: We do not touch any code until the plan is locked. Each step has its own branch, its own tests, its own verification. We never move to the next step if the current one fails.
LOW RISK
Add HF dependency + shared client helper
hf_client.py (NEW) requirements.txt
Create a tiny new file called hf_client.py that returns an OpenAI client pointed at router.huggingface.co/v1. No new packages needed — we reuse openai already installed. Add HF_TOKEN= placeholder to .env. No existing agent code touched at all. This is the foundation everything else builds on.
MEDIUM
Migrate Intake Agent ⚡ Parallel with 3 & 4
intake_agent.py 1 LLM call
The first agent in the chain. Extracts structured patient data (name, room, meds, vitals) from the nurse's transcript. Swap AzureOpenAI client → HF InferenceClient. Speech transcription (Azure Speech) stays completely untouched.
LOW RISK
Migrate Verification Agent ⚡ Parallel with 2 & 4
verification_agent.py 1 LLM call
Checks the handoff data against the patient's EMR record in Supabase. Finds discrepancies — wrong medication, unknown drug, vital out of range. Exact same code pattern as intake agent, straightforward swap.
MEDIUM
Migrate Protocol Agent ⚡ Parallel with 2 & 3
protocol_agent.py 2 LLM calls
Checks clinical protocol compliance — does this patient need a fall risk assessment? Is the ACS protocol being followed? Two separate LLM calls, both need updating. Same code pattern as above, just two places instead of one.
MEDIUM
Migrate Update Agent ⚡ Parallel with 6
update_agent.py 1 LLM call
Handles mid-shift updates — a nurse records "I gave 500mg paracetamol at 3pm". Uses Deepgram (not Azure Speech) for transcription — Deepgram stays untouched. Different import style to the other agents, slightly different change pattern.
HIGH RISK
Migrate Draft Generator ⚡ Parallel with 5
draft_generator.py 3 LLM calls
The most complex agent. Generates the final structured handover document. 3 LLM calls originally running in parallel threads. Free-tier fix: calls are serialised (run one after another) to stay within HF's free rate limit of ~1 req/second. When upgrading to HF Pro, concurrency can be re-enabled in one line.
LOW RISK
Full integration test + cleanup
All files
Run the entire system end-to-end. Verify zero Azure OpenAI references remain in active code. Remove unused openai package from requirements if no longer needed. Update README. Trigger website copy update: "under two minutes" → "under 20 seconds".
The Adversarial Review — What the Critic Found

Issues raised, verified, and resolved

After writing the blueprint, we ran a second AI agent (Opus — the most powerful model) as a "hostile critic" and told it to find every flaw in the plan. Here's what it found and what actually happened when we checked.
Critical — Resolved ✓
C1 · Wrong response_format syntax for HF InferenceClient
The critic claimed that {"type": "json_object"} is an OpenAI-only parameter and would silently fail or crash on HF — meaning agents would return plain text instead of JSON, breaking clinical output.
✅ Verified against actual code: huggingface_hub==1.11.0 has a native ChatCompletionInputResponseFormatJSONObject type that accepts exactly {"type": "json_object"}. The plan is correct as-is. No change needed.
Critical — Resolved ✓
C2 · coordinator_agent.py was never audited for Azure OpenAI usage
The coordinator is the orchestrator that calls all 5 agents. If it had its own Azure OpenAI client, we would have missed it and shipped a broken system.
✅ Read the full file. Confirmed: coordinator_agent.py is a pure orchestrator with zero LLM calls. It only imports and calls the other agents. Nothing to migrate there.
Critical — Resolved ✓
C3 · temperature=0.0 may behave differently on HF (patient safety risk)
Azure OpenAI with temperature=0.0 is greedy deterministic decoding. Some HF backends historically reject 0.0 or silently coerce it to a default (e.g. 1.0), which for clinical data would mean the model paraphrases drug names and dosages — a direct patient safety hazard.
✅ Confirmed temperature: float | None = None is accepted directly by InferenceClient. Value 0.0 passes through to TGI. Added a post-migration determinism test to the plan: same input × 20 runs must produce identical output.
Critical — Resolved ✓
C4 · InferenceClient is not thread-safe — draft_generator uses threading
draft_generator.py runs 3 LLM calls in parallel using Python's concurrent.futures thread pool. If all 3 share the same InferenceClient instance, they share the same internal requests.Session — causing connection pool corruption, header bleed-through, and garbled responses under load.
✅ Fixed in Step 6 of the plan: each lambda in the thread pool now calls get_hf_client() to create a fresh client, rather than sharing one. Thread-safety guaranteed at the cost of 2 extra client initialisations per handover — negligible overhead.
High — Fixed
H1 · max_tokens=1024 too low for multi-resident clinical notes
A 20-resident care home shift handover with vitals, medications, and incident summaries easily exceeds 1024 tokens. The model would truncate mid-JSON — potentially cutting a clinical instruction like "Do not administer" to "Do not".
✅ Bumped to 4096 tokens for draft_generator and protocol_agent in the plan. Also added instruction to detect finish_reason == "length" and fail loudly instead of silently returning truncated output.
